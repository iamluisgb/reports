2. Arquitectura Técnica y Stack Tecnológico

2.1 El Problema de los Datos Fragmentados

El enfoque estándar (migración masiva a Data Lake / Lakehouse) fracasa en empresas con 15+ años de datos en SAP, Oracle EBS, Salesforce, ServiceNow, ERPs legacy y hojas de cálculo. Una migración típica cuesta $5-20M y lleva 18-36 meses — inasumible para startups FDE.

La solución Palantir (replicada): No mover los datos. Construir una capa ontológica virtual sobre los sistemas existentes.

2.3 Ontología+Grafo+LLM vs. Vector Search + RAG Básico

DimensiónVector Search + RAGOntología + Grafo + LLM (GraphRAG)
Precisión factual Depende de chunking + cosine similarity. Recuperación semántica aproximada. Fallo en joins multicapa. Hechos recuperados vía SPARQL/Cypher = exactitud determinista. El LLM solo reformatea.
Alucinaciones Altas. El LLM "rellena" cuando el chunk relevante no aparece en top-K. Bajas. La ontología restringe el espacio de respuestas a hechos verificados. GraphRAG reduce alucinaciones ~40-60% (estudios Microsoft 2024, NebulaGraph 2025).
Consistencia lógica Nula entre queries. Cada query es independiente. No hay noción de "pedido no puede tener estado pagado si no tiene items". SHACL shapes imponen restricciones ontológicas. "Un pedido sin items es inválido" es enforceable en la capa de grafo.
Joins entre sistemas Imposible sin pre-join en índices vectoriales. Cada fuente requiere su propio pipeline de embedding. La ontología modela relaciones cross-system como aristas en el grafo. Consultas federadas SPARQL 1.1.
Evolución del modelo de datos Re-embedding masivo al cambiar esquema. Semanas de reprocesamiento. La ontología evoluciona incrementalmente. Nuevas clases/subclases sin reindexar.
Auditoría / Trazabilidad No hay trazabilidad inherente. "El LLM usó chunk X, pero no sabemos por qué pesó más que Y". Cada respuesta puede mapearse a nodos/aristas concretos del grafo. Trazabilidad completa.
Coste operativo Bajo inicial. Alto a escala (embedding de millones de docs, GPUs para inferencia). Alto inicial (modelado ontológico). Bajo marginal. El grafo es consultable sin LLM para queries simples.
📌 Decisión Arquitectónica: La combinación Ontología+Grafo+LLM no reemplaza al RAG vectorial — lo complementa. El patrón emergente (Digetiers, Stardog, Microsoft GraphRAG) es: GraphRAG híbrido = recuperación por grafo para hechos exactos + vector search para contexto semántico difuso. Un router decide qué canal usar según la query.

2.4 Orquestación Agéntica con Capacidad Read/Write

Patrones de diseño dominantes en producción enterprise (2025-2026):

  • State Graph (LangGraph): El estándar de facto para agentes con múltiples pasos. Cada nodo del grafo es un paso: humano_revisa → extrae_datos → valida → escribe_en_SAP → notifica. El estado se persiste en PostgreSQL/Temporal.io para resiliencia.
  • Human-in-the-Loop obligatorio en writes: Ningún startup FDE serio escribe directamente en producción sin aprobación humana. El patrón: agente prepara payload → humano revisa en UI → agente ejecuta. Invisible Technologies lo tiene como core de su plataforma.
  • Rollback Contracts: Cada operación de escritura va acompañada de un "contract" reversible. Si el agente escribe un cambio incorrecto en el ERP, debe poder deshacerlo dentro de una ventana de tiempo configurable.
  • Circuit Breakers por tenant: Si un agente excede N errores en el mismo sistema en T minutos, se abre el circuito. El FDE interviene manualmente.

Ejemplo concreto (sintetizado de arquitecturas Tomoro y AI/R):

# Pseudo-arquitectura de agente de aprovisionamiento SAP
graph = StateGraph(AgentState)

graph.add_node("extract_order")
graph.add_node("validate_with_ontology")  # SHACL shape check
graph.add_node("human_approval")          # UI + WebSocket
graph.add_node("write_to_sap")            # BAPI/RFC call + rollback contract
graph.add_node("notify")                  # Teams/Slack/Email

graph.add_edge("extract_order", "validate_with_ontology")
graph.add_conditional_edges(
    "validate_with_ontology",
    lambda s: "write_to_sap" if s.validation_passed else "human_approval",
    {"write_to_sap": "write_to_sap", "human_approval": "human_approval"}
)
graph.add_conditional_edges(
    "write_to_sap",
    lambda s: "notify" if s.sap_ok else "human_approval",
)

3.2 Economía del Modelo FDE para una Startup

💰 La Ecuación Fundamental (según a16z):

Fase 1 (Años 1-2): Margen bruto 40-55%. Cada FDE cuesta ~$200-250K/año (todo incluido). Se factura al cliente $300-400K/año por FDE. Diferencial: ~$100-150K/FDE/año. Muy por debajo del 80% que espera el SaaS.

Fase 2 (Años 3-4): El software reutilizable (ontologías, conectores, agent templates) empuja el margen a 65-75%. Se añaden FDEs junior supervisados por seniors (ratio 4:1).

Fase 3 (Año 5+): Plataforma producto + implementation ecosystem. Margen 75-80%. ServiceNow: 63% al IPO → 79% en 2024. Workday: 54% → 75%.

Mecanismos de escalabilidad concreta (observados en Tomoro, Invisible Tech, Resolve AI):

  • Conectores reutilizables: Cada integración con SAP/Salesforce/ServiceNow se convierte en un adapter empaquetado. Próximo cliente similar: el conector ya existe. Coste marginal de integración cae 70%.
  • Ontologías por vertical: Una ontología de supply chain para manufactura es 80% reutilizable entre clientes del mismo sector. Solo el 20% final requiere personalización onsite.
  • Agent Templates: Workflows agénticos comunes (aprobación de facturas, conciliación de pedidos, detección de anomalías en inventario) se empaquetan como "blueprints". El FDE configura, no codea desde cero.
  • Pricing basado en outcomes: En lugar de billing por hora, algunas startups (Invisible Tech, Resolve) cobran un % del ahorro generado o un fee fijo por "agente desplegado y operativo". Alinea incentivos y sube el techo de ingresos.
📌 Señal de Madurez: Invisible Technologies reporta $134M de revenue con este modelo, creciendo 3x año contra año. Han publicado whitepaper explicitando que replican deliberadamente el playbook Palantir pero para el mercado mid-market (empresas de $50M-$2B), que Palantir ignora.

4. Desafíos de Infraestructura, SRE y Gobernanza

4.1 Gestión de Estado en Agentes de Larga Duración

El problema: Un agente que supervisa una orden de compra puede durar semanas: desde la creación hasta la entrega y facturación. El LLM no tiene memoria más allá de su context window. El agente puede ser interrumpido (deploy, crash, escalado).

Soluciones en producción:

  • Checkpointing en base de datos: El estado del grafo (LangGraph) se persiste en PostgreSQL después de cada transición de nodo. Si el agente falla, se reanuda desde el último checkpoint.
  • Temporal.io / Airflow para orquestación larga: Workflows que duran días usan Temporal como "reloj" externo. El agente es una Activity dentro de un Workflow Temporal. Si el agente no responde en N minutos, Temporal lo retry con backoff.
  • State TTL y garbage collection: Estados huérfanos (agente empezó pero nunca terminó) deben tener TTL configurable. Una job cron de limpieza elimina states expired.
  • Event sourcing: Cada acción del agente es un evento inmutable. El estado actual es la proyección de todos los eventos pasados. Permite "rebobinar" y auditar.

4.3 RBAC y Seguridad en la Capa de Ontología

El desafío: Cuando múltiples agentes (cada uno representando a diferentes departamentos/usuarios) interactúan con la misma ontología compartida, el control de acceso no puede estar solo en la aplicación — debe estar en la propia capa ontológica.

Patrón emergente:

  • Ontology-level RBAC (Stardog, d.AP): Cada tripleta/nodo del grafo tiene metadatos de acceso. Un agente de RRHH no puede leer triplas de nómina aunque estén en el mismo grafo que datos de empleados públicos.
  • Filtrado SPARQL/Cypher automático: La query del LLM se reescribe antes de ejecutarse: SELECT ?factura WHERE { ... } → SELECT ?factura WHERE { ... FILTER(?departamento = "ventas") }. El rewriter añade condiciones de RBAC basadas en la identidad del agente.
  • Data masking en respuestas del grafo: Si un agente no tiene permiso para ver el campo "coste" de un pedido, la ontología devuelve null o *** en lugar del valor real. El LLM nunca ve el dato.
  • Audit log por tripleta: Cada acceso a un nodo/arista del grafo se loguea con: agente_id, timestamp, query, resultado devuelto. Permite auditoría forense: "¿qué agente vio qué datos y cuándo?"
📌 Advertencia SRE: El mayor riesgo en producción no es que la IA tome una decisión incorrecta — es que la IA actúe sobre una decisión incorrecta sin supervisión. Toda acción de escritura debe pasar por: (1) validación ontológica, (2) rate limiting, (3) human approval gate, (4) circuit breaker, (5) rollback contract. Sin estos 5 gates, un agente puede causar daños en segundos que un humano tardaría semanas en reparar.

5. Anti-patrones y Modos de Fallo Habituales

⚠️ Esta sección es la más importante del informe. Basada en fracasos documentados de startups que intentaron replicar el modelo Palantir sin entender sus limitaciones estructurales.

Anti-patrón #1: "Ontología al Día 1"

Error: Intentar modelar la ontología completa de la empresa antes de tener un solo agente funcionando.

Modo de fallo: Meses de modelado sin valor demostrable. La ontología es demasiado abstracta o incorrecta. El cliente pierde la paciencia.

Correcto: Ontología mínima viable (3-5 clases, 5-10 relaciones). Suficiente para resolver el primer caso de uso. La ontología evoluciona con cada nuevo agente. Palantir llama a esto "ontogénesis" — la ontología crece orgánicamente con el uso.

Anti-patrón #2: "FDE únicos sin plataforma"

Error: Contratar FDEs pero no invertir en plataforma reutilizable. Cada FDE resuelve cada problema desde cero.

Modo de fallo: La startup es una consultora glorificada. Margen 20-30%, no 40-55%. Escalar = contratar más FDEs, no más software. El modelo no es sostenible.

Correcto: Todo FDE debe dedicar 20-30% de su tiempo a crear conectores, templates y componentes reutilizables. El ratio plataforma/servicios debe mejorar cada trimestre.

Anti-patrón #3: "Agentes autónomos sin gates"

Error: Confiar en que el LLM no va a alucinar una operación de escritura en producción. "El modelo es muy bueno, no va a fallar".

Modo de fallo: Un agente escribe 10,000 registros incorrectos en SAP porque el prompt tenía un ejemplo ambiguo. El cliente exige compensación o se va.

Correcto: Human-in-the-loop obligatorio en writes durante los primeros 6 meses de cada cliente. Solo después, modo semi-autónomo con approval por excepción. Los 5 gates de seguridad son no-negociables.

Anti-patrón #4: "Benchmarking con Palantir en features"

Error: Intentar igualar el feature set de Foundry/Gotham. Palantir tiene 20 años y 3,000+ ingenieros.

Modo de fallo: Producto sobreingenierizado para un mercado que no necesita el 80% de las features. Tiempo de desarrollo perdido. Confusión del cliente.

Correcto: Competir en simplicidad + velocidad de implementación + precio. El cliente elige a la startup no porque tenga más features, sino porque un FDE está onsite esta semana y Palantir tarda 6 meses en hacer un POC.

Anti-patrón #5: "Ignorar la seguridad por defecto"

Error: No implementar RBAC ontológico desde el día 1. Asumir que "luego se añade".

Modo de fallo: Auditoría de seguridad del cliente descubre que un agente de ventas podía ver datos financieros. El deal se cae. El cumplimiento regulatorio (GDPR, SOX, HIPAA) se vuelve blocker.

Correcto: RBAC ontológico es parte del MVP. Cada tripleta hereda permisos de su clase. Por defecto: denegar todo, permitir explícitamente.

Anti-patrón #6: "Subestimar el coste de modelado ontológico"

Error: Asumir que LLMs pueden generar la ontología automáticamente con un prompt.

Modo de fallo: Ontología inconsistente, redundante, con errores lógicos. SHACL validation falla en cada esquina. Los agentes toman decisiones basadas en relaciones incorrectas.

Correcto: El LLM asiste, no reemplaza. La ontología la define un ingeniero ontológico (o un FDE entrenado en modelado semántico) en colaboración con expertos de dominio del cliente. El LLM puede sugerir relaciones, pero un humano valida cada una.

6. Conclusiones y Ventana de Oportunidad

🎯 Síntesis para Decisión Estratégica:

1. El modelo FDE + ontología está validado por exits de alto perfil (OpenAI-Tomoro, Accenture-Faculty) y por la tesis explícita de a16z. No es experimental — es el nuevo estándar de entrada para IA enterprise.

2. Existe un gap claro: ninguna startup combina plataforma ontológica (como Foundry) + modelo FDE + precio mid-market. Digetiers/d.AP tiene la plataforma pero engagement tipo consultoría. Invisible Technologies tiene el modelo FDE pero plataforma distinta. Oportunidad para el "Palantir para empresas medianas".

3. El cuello de botella no es técnico — es talento FDE. OpenAI pagó un premium por Tomoro (~150 FDEs) precisamente porque no se pueden "entrenar" rápido. Cualquier startup seria debe construir su pipeline de FDE desde el día 1.

4. La ventana de oportunidad es 12-18 meses. Palantir está moviéndose a mid-market con AIP. Los hyperscalers están construyendo sus propias capas de implementación. El momento de construir es ahora.
