Skillify: gbrain's Meta-Skill

2 JUN 2026
The 11-point framework for building production-grade agent skills · Cross-modal evaluation · The definitive checklist
Executive Summary

Skillify is the meta-skill inside Garry Tan's gbrain project — an 11-point quality framework that turns any raw feature into a properly instrumented, evaluated, and tested agent skill. It is not a simple SKILL.md generator. It is an engineering discipline for production-grade skills.

The core idea is radically simple but surgically executed: prove quality first, then freeze it with tests. The heart of the system is a cross-modal evaluation where 3 frontier models from 3 different providers — typically GPT-4o, Claude Opus 4.7, and Gemini 1.5 Pro — evaluate the skill's output across 5 dimensions before a single line of test code is written.

Dimension Description Threshold
Goal AdherenceDoes the output meet the stated objective?≥7/10

SpecificityIs it concrete or generic?≥7/10
StructureIs the organization clear?≥7/10
ActionabilityCan someone act on it?≥7/10

Every skill that passes the process receives a quality certificate: a JSON receipt signed with the SHA-8 of the SKILL.md, allowing anyone to verify at any time whether the skill is current or has gone stale after changes.

What Is gbrain and Why Its Skillify Matters

gbrain is Garry Tan's personal agent system (founder of Initialized Capital, former Y Combinator president). It's an open-source project at github.com/garrytan/gbrain that implements a memory-centric agent architecture (15 entity types, brain as knowledge base, skills as capability units). In this ecosystem, skills aren't loose scripts — they are software components with tests, evaluations, and governed resolution routing.

gbrain's skillify skill is the skill that builds skills. It's the meta-skill: it takes raw functionality and transforms it into a properly instrumented agent capability unit following an 11-item checklist. Each item represents a quality milestone a skill must clear to be considered "properly skilled."

What sets this approach apart from other skill generators (like kk-r/skillify-skill, which converts sessions into SKILL.md) is the depth of the quality process. While most tools focus on file generation, gbrain skillify focuses on verification and validation of the skill as a software artifact.

The 11-Point Checklist

A skill is not complete until all 11 items pass. Item 3 (cross-modal eval) is informational in v1.1.0 — it doesn't block the audit but surfaces visibly if missing. Items 1-10 are mandatory; item 11 only applies if the skill writes to the brain.

The gbrain skillify check command produces a three-tier verdict:

  • properly skilled — all mandatory items pass
  • close — create: <missing items> — close but incomplete
  • needs skillify — run /skillify on <target> — hasn't been touched

JSON output lets agents route on the structured envelope without parsing prose.

The Heart: Cross-Modal Evaluation

gbrain skillify's most important innovation is cross-modal evaluation as a quality gate before tests. The philosophy is clear: "Tests lock in behavior. If the behavior is mediocre, tests lock in mediocrity."

The flow is:

Step 1: Representative Input

Choose the input that exercises the skill's hardest documented use case. When in doubt: the primary trigger example from SKILL.md, or the most complex real-world input from the last 7 days of sessions.

Step 2: Run the Skill

Execute the skill against that input. The output file is what gets evaluated.

Step 3: Run the Eval Gate

gbrain eval cross-modal \
  --task "What this skill is supposed to accomplish" \
  --output skills/<slug>/SKILL.md

This launches 3 frontier models from 3 different providers in parallel. Each model scores the output against the task across 5 dimensions. The result is a JSON receipt at ~/.gbrain/.gbrain/eval-receipts/<slug>-<sha8>.json — the SHA-8 binds the receipt to the exact SKILL.md content.

Slot Default Model Provider
Aopenai:gpt-4oOpenAI
Banthropic:claude-opus-4-7Anthropic
Cgoogle:gemini-1.5-proGoogle

Pass criteria (BOTH must be true):

  1. Every dimension's mean across successful models ≥ 7
  2. No single model scored any dimension < 5 (the floor)

Inconclusive: fewer than 2 of 3 models returned parseable scores. The receipt is still written (forensics) but the gate is not authoritative. Exit code 2.

Step 4: Improvement Cycle (≤3 cycles)

The typical cycle:

  • Cycle 1: Eval → get scores + top 10 improvements. If it passes, move to tests. If not, apply improvements to the real file.
  • Cycle 2: Re-eval the corrected output. Compare deltas per dimension. If it passes, move to tests.
  • Cycle 3 (final): Re-eval. If it passes, ship. If not, ship with a KNOWN_GAPS section documenting what couldn't be resolved and why.

Cost guardrails: defaults to 3 cycles in TTY, 1 in non-TTY. $1–3 per full run with Opus-class + GPT-4o + Gemini-1.5-Pro at --max-tokens 4000. Receipts include per-call model identifiers for retroactive audit.

Skip the eval when: the output is < 200 tokens (trivial, not worth 9 API calls) or the skill is a thin wrapper around a single API call (1 cycle is enough).

Complete Pipeline: All 7 Phases

gbrain skillify isn't just the eval. It's a 7-phase pipeline covering the full skill lifecycle:

Phase 0: Should This Be a Skill?

Entry gate before investing time:

  • Will it be invoked 2+ times? (One-off work ≠ skill)
  • Is there >20 lines of logic? (Trivial helpers don't need full infrastructure)
  • Does it have a clear trigger phrase a user would actually say?

If no to all three: it's a script, not a skill.

Phase 1: Audit

Feature, code path, missing items from the 11-point checklist.

Phase 2: Write SKILL.md + Code

Standard frontmatter (name, version, description, triggers, tools, mutating). Body with Contract + Phases + Output Format. Deterministic code extracted into scripts.

Phase 3: Cross-Modal Eval (the quality gate)

As described above. Up to 3 cycles of eval → improve → re-eval.

Phase 4: Tests (after the eval)

Unit + Integration + LLM evals. Now that quality is proven, tests freeze it.

Phase 5: Resolver + Check-Resolvable

Entry in RESOLVER.md with real user phrases. Routing test. DRY + MECE audit.

Phase 6: E2E + Brain Filing

Full pipeline smoke test. Brain/RESOLVER.md entry if applicable.

Phase 7: Verify

bun test test/<skill>.test.ts                    # unit tests
gbrain skillify check skills/<slug>/scripts/<slug>.mjs --json | \
  jq '.[] | .items[] | select(.name | contains("Cross-modal"))'
ls ~/.gbrain/.gbrain/eval-receipts/              # receipt landed
gbrain check-resolvable --json | jq .ok          # resolver clean

Documented Anti-Patterns

gbrain skillify explicitly documents what NOT to do. This is as valuable as the checklist itself:

  • ❌ Tests before cross-modal eval — you cement mediocrity
  • ❌ Budget models for eval — a C student grading an A student
  • ❌ Single provider for all 3 slots — correlated blind spots
  • ❌ Skipping eval "because the output looks fine" — your judgment isn't 3 models
  • ❌ Eval without a fix cycle — vanity metrics
  • ❌ Code without SKILL.md — invisible to the resolver
  • ❌ Tests that reimplement production code — mask real bugs
  • ❌ Resolver entry with internal jargon — must mirror real user language
  • ❌ Two skills doing the same thing — merge or kill one
  • ❌ Cross-modal eval on trivial outputs — < 200 tokens doesn't warrant 9 API calls
