Skillify: El Meta-Skill de gbrain

2 JUN 2026
El marco de 11 puntos para construir skills de agente con calidad de producción · Evaluación cross-modal · El checklist definitivo
Resumen Ejecutivo

Skillify es el meta-skill dentro del proyecto gbrain de Garry Tan — un framework de calidad en 11 puntos para transformar cualquier funcionalidad en un skill de agente correctamente instrumentado, evaluado y testeado. No es un simple generador de SKILL.md. Es una disciplina de ingeniería para skills de producción.

La idea central es radicalmente simple pero ejecutada con precisión quirúrgica: primero demuestra calidad, luego congélala con tests. El corazón del sistema es una evaluación cross-modal donde 3 frontier models de 3 providers distintos — típicamente GPT-4o, Claude Opus 4.7 y Gemini 1.5 Pro — evalúan la salida del skill en 5 dimensiones antes de escribir una sola línea de test.

Dimensión Descripción Umbral
Goal Adherence¿La salida cumple el objetivo declarado?≥7/10
Depth¿Qué tan profundo es el análisis?≥7/10
Specificity¿Es concreta o genérica?≥7/10
Structure¿La organización es clara?≥7/10
Actionability¿Se puede actuar sobre ella?≥7/10

Cada skill que pasa el proceso obtiene un certificado de calidad: un receipt JSON firmado con el SHA-8 del SKILL.md que permite verificar en cualquier momento si el skill está al día o si ha quedado obsoleto tras cambios.

¿Qué es gbrain y por qué su skillify importa?

gbrain es el sistema de agente personal de Garry Tan (fundador de Initialized Capital, expresidente de Y Combinator). Es un proyecto abierto en github.com/garrytan/gbrain que implementa una arquitectura de agente centrada en memoria (15 tipos de entidades, brain como base de conocimiento, skills como unidades de capacidad). En este ecosistema, los skills no son scripts sueltos — son componentes de software con tests, evaluaciones y resolución gobernada.

El skill skillify de gbrain es el skill que construye skills. Es el meta-skill: toma una funcionalidad cruda y la transforma en una unidad de capacidad de agente correctamente instrumentada siguiendo un checklist de 11 items. Cada item representa una etapa de calidad que un skill debe superar para ser considerado "properly skilled".

Lo que distingue este enfoque de otros generadores de skills (como kk-r/skillify-skill, que convierte sesiones en SKILL.md) es la profundidad del proceso de calidad. Mientras la mayoría de las herramientas se centran en la generación del archivo, gbrain skillify se centra en la verificación y validación del skill como artefacto de software.

El Checklist de 11 Puntos

Un skill no está completo hasta que los 11 items pasan. El item 3 (cross-modal eval) es informativo en v1.1.0 — no bloquea el audit pero aparece como visible si falta. Los items 1-10 son obligatorios; el 11 solo aplica si el skill escribe en el brain.

# Item Fase Qué Verifica
1SKILL.mdEstructuraFrontmatter + contrato + fases. El archivo existe y sigue el estándar.
2CódigoEstructuraScript determinista si aplica. No todo cabe en SKILL.md.
3Cross-modal evalCalidad3 frontier models evalúan la salida. Informativo, no bloqueante.
4Unit testsTestsCubren cada rama de lógica determinista. Sin mockear el cielo.
5Integration testsTestsEjercitan endpoints reales. Pillan bugs que los mocks esconden.
6LLM evalsTestsCasos de calidad para pasos con LLM. Más ligeros que cross-modal.
7Resolver triggerDescubrimientoEntrada en RESOLVER.md con frases reales de usuario.
8Resolver evalDescubrimientoTest de que los triggers enrutan al skill correcto.
9Check-resolvableDescubrimientoDRY + MECE audit. Sin skills huérfanos, sin solapamientos.

11Brain filingMemoriaSolo aplica si escribe en la base de conocimiento. Check de entrada en brain/RESOLVER.md.

El comando gbrain skillify check produce un veredicto en tres niveles:

  • properly skilled — todos los items obligatorios pasan
  • close — create: <items faltantes> — cerca pero incompleto
  • needs skillify — run /skillify on <target> — ni empezado

El output JSON permite a los agentes enrutar sobre el sobre estructurado sin parsear prosa.

El Corazón: Evaluación Cross-Modal

La innovación más relevante de gbrain skillify es la evaluación cross-modal como quality gate antes de los tests. La filosofía es clara: "Tests lock in behavior. If the behavior is mediocre, tests lock in mediocrity."

El flujo es:

Paso 1: Representative Input

Se elige el input que ejercita el caso de uso más complejo del skill. Si hay duda: el ejemplo de trigger principal del SKILL.md, o el input real más complejo de los últimos 7 días de sesiones.

Paso 2: Ejecutar el Skill

Se corre el skill sobre ese input. El archivo de salida es lo que se evalúa.

Paso 3: Ejecutar el Eval Gate

gbrain eval cross-modal \
  --task "What this skill is supposed to accomplish" \
  --output skills/<slug>/SKILL.md

Esto lanza 3 frontier models de 3 providers distintos en paralelo. Cada modelo puntúa la salida contra la tarea en 5 dimensiones. El resultado es un receipt JSON en ~/.gbrain/.gbrain/eval-receipts/<slug>-<sha8>.json — el SHA-8 vincula el receipt al contenido exacto del SKILL.md.

Slot Modelo por Defecto Provider
Aopenai:gpt-4oOpenAI
Banthropic:claude-opus-4-7Anthropic
Cgoogle:gemini-1.5-proGoogle

Criterio de paso (AMBOS deben cumplirse):

  1. Cada dimensión con media ≥ 7 entre los modelos que respondieron
  2. Ningún modelo puntuó ninguna dimensión < 5 (el suelo)

Inconcluso: menos de 2 de 3 modelos devuelven puntuaciones parseables. El receipt se escribe igual (forense) pero la puerta no es autoritativa. Exit code 2.

Paso 4: Ciclo de Mejora (≤3 ciclos)

El ciclo típico:

  • Ciclo 1: Evalúa → recibe puntuaciones + top 10 mejoras. Si pasa, a tests. Si no, aplica las mejoras al archivo real.
  • Ciclo 2: Re-evalúa la salida corregida. Compara deltas por dimensión. Si pasa, a tests.
  • Ciclo 3 (final): Re-evalúa. Si pasa, ship. Si no, ship con sección KNOWN_GAPS documentando qué no se pudo resolver y por qué.

Guardrails de coste: por defecto 3 ciclos en TTY, 1 en no-TTY. $1–3 por run completo con modelos Opus-class + GPT-4o + Gemini-1.5-Pro en --max-tokens 4000. Los receipts incluyen identificadores de modelo por llamada para auditoría retroactiva.

Skip el eval cuando: la salida es < 200 tokens (trivial, no vale 9 llamadas API) o el skill es un wrapper fino alrededor de una sola llamada API (1 ciclo basta).

Fases Completas del Proceso

El skillify de gbrain no es solo el eval. Es un pipeline de 7 fases que cubre todo el ciclo de vida de un skill:

Fase 0: ¿Debería Ser un Skill?

Gate de entrada antes de invertir tiempo:

  • ¿Se invocará 2+ veces? (Trabajo de una vez ≠ skill)
  • ¿Tiene >20 líneas de lógica? (Helpers triviales no necesitan infraestructura completa)
  • ¿Tiene una frase de activación clara que un usuario diría realmente?

Si no a las tres: es un script, no un skill.

Fase 1: Auditoría

Feature, código, items faltantes del checklist de 11.

Fase 2: Escribir SKILL.md + Código

Frontmatter estándar (name, version, description, triggers, tools, mutating). Cuerpo con Contract + Phases + Output Format. Código determinista extraído a scripts.

Fase 3: Evaluación Cross-Modal (el quality gate)

Como se describió arriba. Hasta 3 ciclos de evalúa → mejora → re-evalúa.

Fase 4: Tests (después del eval)

Unit + Integration + LLM evals. Ahora que la calidad está probada, los tests la congelan.

Fase 5: Resolver + Check-Resolvable

Entrada en RESOLVER.md con frases reales de usuario. Test de enrutamiento. Auditoría DRY + MECE.

Fase 6: E2E + Brain Filing

Smoke test full pipeline. Entrada en brain/RESOLVER.md si aplica.

Fase 7: Verify

bun test test/<skill>.test.ts                    # unit tests
gbrain skillify check skills/<slug>/scripts/<slug>.mjs --json | \
  jq '.[] | .items[] | select(.name | contains("Cross-modal"))'
ls ~/.gbrain/.gbrain/eval-receipts/              # receipt landed
gbrain check-resolvable --json | jq .ok          # resolver clean

Anti-Patrones Documentados

El skillify de gbrain documenta explícitamente lo que NO hacer. Esto es tan valioso como el checklist:

  • ❌ Tests antes de cross-modal eval — cementas mediocridad
  • ❌ Modelos budget para eval — un estudiante C evaluando a un estudiante A
  • ❌ Un solo provider para los 3 slots — blind spots correlacionados
  • ❌ Saltar el eval "porque la salida se ve bien" — tu juicio no son 3 modelos
  • ❌ Eval sin ciclo de fix — métricas de vanidad
  • ❌ Código sin SKILL.md — invisible para el resolver
  • ❌ Tests que reimplementan producción — esconden bugs reales
  • ❌ Resolver entry con jerga interna — debe reflejar lenguaje real del usuario
  • ❌ Dos skills haciendo lo mismo — merge o kill
  • ❌ Cross-modal eval en salidas triviales — < 200 tokens no merece 9 llamadas API
gbrain skillify vs. kk-r/skillify-skill

Son herramientas complementarias, no competidoras. La diferencia fundamental:

Dimensión kk-r/skillify-skill gbrain skillify
PropósitoGenerar SKILL.md desde sesionesCertificar calidad de skills
InputConversación + git diffCódigo + SKILL.md existente
OutputArchivo SKILL.md portableReceipt de calidad + tests + resolver entries
Lo que verificaNada — es generativo11 items de calidad, eval cross-modal
InteracciónEntrevista al usuario (4 rondas)Auditoría automática + ciclo eval
Filosofía"Captura el workflow""Demuestra calidad antes de congelar"
PúblicoCualquier usuario de Claude CodeDesarrolladores de agentes avanzados
DependenciasNinguna — SKILL.md purogbrain CLI, API keys de 3 providers

En la práctica, se pueden encadenar: usas kk-r/skillify-skill para generar el SKILL.md inicial desde una sesión, y luego ejecutas gbrain skillify para llevarlo a calidad de producción con el checklist completo.

Relevancia para Quirón y Tu Stack

Tienes un ecosistema de skills en Hermes Agent: desde el daily-digest hasta herramientas de SRE, GTD, fitness y contenido. El framework de gbrain skillify se aplica directamente:

1. Quality Gate para Skills Críticos

Skills como daily-digest (crítico para tu marca personal) o gtd-capture (crítico para tu sistema personal) se beneficiarían de pasar por un proceso de calidad similar. No necesitas implementar todo el pipeline de gbrain — pero el principio de eval cross-modal antes de tests es aplicable hoy.

2. El Checklist de 11 Items como Referencia

Tus skills actuales: ¿tienen resolver triggers? ¿tests? ¿e2e? ¿check de no solapamiento? El checklist es un estándar concreto contra el que auditar tu /hermes-home/skills/.

3. Evaluación Cross-Modal en Quirón

Quirón es tu agente orquestador. Podrías implementar un skill propio de evaluación de calidad que, cuando terminas un skill nuevo, lance una evaluación similar con los modelos que tengas disponibles (DeepSeek V4, Claude, etc.) antes de marcarlo como "producción".

4. El Principio "Evalúa Primero, Testea Después"

Es aplicable a cualquier artefacto que produces: no solo skills, sino también playbooks, runbooks, contenido para LinkedIn/X. Evalúa la calidad con modelos antes de publicar, no después.

Ecosistema: El Formato SKILL.md como Estándar

Skillify no existe en el vacío. Es parte de un ecosistema que explotó en 2025-2026 alrededor del formato agentskills.io — un estándar abierto de SKILL.md que hoy es compatible con 30+ plataformas de agente: Claude Code, Cursor, Copilot, Gemini CLI, Codex CLI, VS Code, y más.

Skillify de gbrain se posiciona en la capa de creación con calidad — el paso entre "tengo una idea para un skill" y "tengo un skill de producción que no va a romper nada".

Conclusiones y Próximos Pasos

Skillify de gbrain es, probablemente, el marco de calidad para skills de agente más completo disponible públicamente hoy. No es una herramienta que uses para generar skills — es una disciplina que aplicas para garantizar que tus skills no son basura.

Tres acciones concretas que puedes tomar:

  1. Auditar tu sistema de skills actual contra el checklist de 11 items. ¿Cuántos skills de Hermes tienen tests? ¿Cuántos tienen resolver triggers con frases reales de usuario?
  2. Implementar un skill de "quality gate" en Quirón — una versión ligera del cross-modal eval que, al terminar un skill nuevo, lo evalúe contra criterios de calidad antes de integrarlo.
  3. Adoptar el principio "evalúa primero, testea después" — no solo para skills, sino para cualquier artefacto que produzcas con ayuda de IA: contenido, runbooks, playbooks, código.

El meta-skill de gbrain demuestra que la industria de agentes está madurando: ya no basta con tener un skill que funcione "más o menos". Los skills son unidades de software, y merecen el mismo nivel de ingeniería que cualquier otro componente de producción.
